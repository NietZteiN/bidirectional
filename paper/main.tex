\begin{abstract}
Fine-tuning a language model to perform a task in one direction can improve that task
while weakening its ability to work in the reverse direction. We study this tradeoff
across seven task families and test a simple intervention: replace a small share of forward
training pairs with their reversals. For example, in format conversion, $1\%$ reversed
pairs yield \NUM{main-fmt-mix1-backward}\% backward success, compared with
\NUM{main-fmt-sft-backward}\% under forward-only training, while forward performance
is nearly unchanged. The intervention starts from the base model and keeps training-example
counts and optimizer steps fixed. Benefits extend to code, translation, and semantic parsing,
although the useful proportion and forward costs vary by task. Comparisons with contrastive
and other auxiliary objectives show why ordinary reversed-pair training is an essential
baseline for evaluating preservation methods.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A translation pair can train either language direction. A question--SQL pair can train
semantic parsing or question generation. Although the same pair supplies both tasks,
training on one direction need not preserve the other. Prior work documents directional
degradation in code transformation \citep{nikiema2025contrastive} and translation
\citep{zhu2024finetuning}. Evaluating only the trained direction can therefore miss a
substantial loss of an existing capability.

The practical intervention is simple: replace some forward examples with their reversed
pairs and train with ordinary cross-entropy (CE) loss. In our formatting comparison,
forward-only supervised fine-tuning (SFT) improves forward success from \NUM{main-fmt-base-forward}\% to
\NUM{main-fmt-sft-forward}\%, but backward success falls from
\NUM{main-fmt-base-backward}\% to \NUM{main-fmt-sft-backward}\%.
With $1\%$ reversal, backward success is \NUM{main-fmt-mix1-backward}\% and forward
success is \NUM{main-fmt-mix1-forward}\%. The mixture is trained from the base checkpoint;
it prevents much of the backward loss rather than repairing an already collapsed model
with additional data.

We make three connected contributions. First, we characterize forward/backward
tradeoffs across task families, models, and training runs. Second, we measure how those
tradeoffs change with the proportion of reversed pairs. Third, we test whether specialized
objectives add benefits beyond ordinary directional supervision. Across several tasks,
small reversal proportions preserve backward performance while retaining most forward
gains. This changes how preservation methods should be evaluated: a specialized objective
must show what it adds beyond simply training on the reverse mapping.

\section{Paired tasks and directional degradation}
\label{sec:defined}

A paired instance contains two sides $(x,y)$, together with any required context such as a
function or database schema. The forward task generates $y$ from $x$; the backward task
generates a valid $x$ from $y$. Reversing a paired task need not mean uniquely reconstructing
a string: translations and questions admit paraphrases, and a function can have several
inputs producing the same output. Correctness follows the requested task, rather than
reference-string matching whenever a semantic check is available.

We call any reduction in backward success after forward-only training \emph{directional
degradation}. For descriptive counting and highlighting, \emph{severe directional collapse}
means backward success at most half the base-model rate. This threshold describes the
size of a loss; it is not a significance test. All comparisons use the base model evaluated
on the same held-out examples as the fine-tuned models.

\section{Tasks and experimental setup}
\label{sec:setup}
\input{tables/task_definitions.tex}

\paragraph{What the model must produce.}
Table~\ref{tab:task-definitions} defines the seven task families and their correctness
checks. Translation contributes four training orientations and algebra two, giving
\NUM{core-domain-count} orientations in the main comparison; opposite orientations are
not independent datasets. Formatting converts JSON to YAML/XML and Markdown tables to
CSV, with the backward tasks converting back. Code pairs readable Python with five
obfuscation styles. Execution prediction supplies the function in both directions and
accepts any input producing the required backward output.
Unit conversion is an additional boundary experiment outside these seven families,
testing whether forward training necessarily harms reverse performance
(Appendix~\ref{app:boundaries}).

\paragraph{What success means.}
Each answer receives a binary, task-specific correctness score; strict success is the
percentage satisfying that predicate. Format outputs must parse with the target parser,
match the underlying data, and avoid copying the input. Copying matters particularly for
JSON-to-YAML: JSON also parses as YAML. The copy guard rejects this trivial behavior,
although the original scorer does not require syntax exclusive to YAML. Code correctness
primarily measures agreement on execution tests, not recovery of original identifier names.
Algebra checks symbolic equivalence; factoring also requires a product form, while the
expansion scorer has no separate expanded-form requirement.

Translation requires the target language and COMET-22 above a threshold fixed from each
base model's score distribution before tuned evaluation. Thresholds differ by model and
direction, so success percentages compare training methods within a model, not absolute
translation quality across models. The original forward translation check lacks the
backward check's explicit copy rejection. SQL generation uses database execution; backward
question generation is scored by parsing the question with a frozen Granite model and
checking the resulting query. This model-based check can reject valid paraphrases.
The other proposed model-based check, WebNLG triples-to-text, has an unreliable reference
extractor and contributes no tuned result. Exact prompts, parsing rules, thresholds,
source versions and split sizes are consolidated in Appendix~\ref{app:task-scoring}.

\paragraph{Training data and intervention.}
The retained training sizes are in Table~\ref{tab:task-definitions}. In the reference
formatting run, $1\%$ means \NUM{main-fmt-mix1-pairs} reversed pairs among
\NUM{main-fmt-training-pairs}; in code it means \NUM{main-code-mix1-pairs} among
\NUM{main-code-training-pairs}. The actual integer counts depend on grouping and filtering;
the appendix reports both nominal proportions and realized counts.
Forward-only SFT uses all pairs in the forward direction. A replacement mixture partitions
pairs by identity, keeping grouped variants of a program or country together, and replaces
the selected examples with their reversals. No underlying pair is trained in both directions
in a replacement mixture. Every mixture starts from the base model. Training-example counts,
epochs, and optimizer steps match forward SFT. This does not guarantee equal token counts,
runtime, or floating-point operations (FLOPs); detailed accounting is in
Appendix~\ref{app:dose-summary}.

Let $I_F$ and $I_B$ be the forward and backward instructions, and partition training pairs
$D$ into unreversed $F_\rho$ and reversed $B_\rho$ at replacement proportion $\rho$.
With target-completion loss $\ell_\theta$, the schematic pair-level objective is
\begin{equation}
\begin{aligned}
\mathcal L_\rho = \frac{1}{|D|}\Big[&
\sum_{(x,y)\in F_\rho}\ell_\theta(y\mid I_F,x)\\
&+\sum_{(x,y)\in B_\rho}\ell_\theta(x\mid I_B,y)\Big].
\end{aligned}
\label{eq:replacement}
\end{equation}
At $\rho=0$, the model trains only on forward targets. Reversing selected pairs directly
supervises the backward conditional using the same underlying relationship.

\paragraph{Models, controls and uncertainty.}
We evaluate Llama 3B/8B, Gemma 4B/12B, and OLMo 1B, primarily with LoRA. The main
reference comparison uses Llama 3B; additional models and training runs appear in
Appendix~\ref{app:complete-main-comparisons}. Generic instruction replay replaces half
of task examples, backward-only training tests backward learnability, and longer-forward
and both-direction controls use additional budget. The full dose ladder and controls are
in Table~\ref{tab:full-adaptations}. A common effective batch and final-checkpoint recipe
are detailed in Appendix~\ref{app:reference-methods}. Paired cluster-bootstrap intervals
measure uncertainty over test examples; ranges across training runs separately show
training variability. Neither repeated tasks nor resampled test examples count as independent
task families.

\section{Forward gains can hide backward losses}
\label{sec:general}
\input{tables/main_adaptations.tex}

Forward-only SFT substantially reduces backward performance in several tasks, sometimes
while improving forward performance. Formatting gives the clearest example: forward
success rises from \NUM{main-fmt-base-forward}\% to \NUM{main-fmt-sft-forward}\%,
while backward success falls from \NUM{main-fmt-base-backward}\% to
\NUM{main-fmt-sft-backward}\%. Code transformation shows a similar tradeoff: forward
success rises from \NUM{main-code-base-forward}\% to \NUM{main-code-sft-forward}\%,
but backward success falls from \NUM{main-code-base-backward}\% to
\NUM{main-code-sft-backward}\%. Forward improvement alone would miss both losses.

Across the broader set of \NUM{audited-core-cells} evaluated model--task--training-run
combinations, \NUM{core-collapse-cells} meet the severe backward-loss threshold.
Table~\ref{tab:core-inventory} gives model coverage; these are descriptive counts,
not pooled significance tests. Variation is substantive: German-to-English training
also harms forward translation in the reference run, whereas factual-relation SFT improves
both directions. Repeated unit-conversion experiments likewise improve both directions
under the original recipe (Appendix~\ref{app:boundaries}). Directional loss is therefore
a property to measure, not a necessary outcome of fine-tuning.

\section{Small backward doses with ordinary SFT}
\label{sec:dose}

A small share of reversed pairs can prevent large backward losses, but the useful share
depends on the task and direction.

\paragraph{Large gains from small proportions.}
Formatting backward success is \NUM{main-fmt-mix1-backward}\% with $1\%$ reversal and
\NUM{main-fmt-mix5-backward}\% with $5\%$, versus \NUM{main-fmt-sft-backward}\% under
forward-only SFT. Code backward success is \NUM{main-code-mix1-backward}\% at $1\%$
versus \NUM{main-code-sft-backward}\%, while forward success changes from
\NUM{main-code-sft-forward}\% to \NUM{main-code-mix1-forward}\%.
Generic replay and doubled forward training do not yield comparable backward benefits
in these comparisons (Table~\ref{tab:full-adaptations}). More forward optimization is
not a substitute for supplying backward targets.

The $1\%$ benefits recur across \NUM{main-repeat-fmt-runs} formatting runs and
\NUM{main-repeat-code-runs} code runs with different training seeds.
Table~\ref{tab:main-seed-variation} reports the range of forward and backward changes
for every task with repeated low-dose measurements.

\paragraph{Preservation beyond code and formatting.}
In English-to-Chinese training, backward translation success is
\NUM{main-mt-en-zh-mix1-backward}\% with $1\%$ reversal versus
\NUM{main-mt-en-zh-sft-backward}\% with forward SFT. Forward success changes from
\NUM{main-mt-en-zh-sft-forward}\% to \NUM{main-mt-en-zh-mix1-forward}\%, revealing
a cost. In question-to-SQL training, backward question success rises from
\NUM{main-sql-sft-backward}\% to \NUM{main-sql-mix1-backward}\% at $1\%$ and
\NUM{main-sql-mix5-backward}\% at $5\%$; forward success at $1\%$ is
\NUM{main-sql-mix1-forward}\% versus \NUM{main-sql-sft-forward}\%.
Figure~\ref{fig:dose-tradeoff-draft} displays the joint forward/backward comparison;
the gains must be assessed alongside these forward costs.

\paragraph{The useful dose depends on the task.}
When training polynomial expansion, $1\%$ reversed pairs bring backward factorization
success to \NUM{main-algebra-mix1-backward}\%, close to the base rate of
\NUM{main-algebra-base-backward}\%. The opposite training orientation behaves differently:
when training factorization, $1\%$ reversal lowers backward expansion success from
\NUM{main-algebra-rev-sft-backward}\% to \NUM{main-algebra-rev-mix1-backward}\%.
At $5\%$ it is \NUM{main-algebra-rev-mix5-backward}\%. Thus a dose that maintains one
conditional can harm the other; the mixture must be judged jointly with forward performance
and relative to the existing capability. The adverse $1\%$ expansion result occurs in all
\NUM{main-repeat-algebra-rev-runs} factorization-training runs. A uniform $1\%$ rule
would obscure this finding.

The full ladder evaluates $1$, $5$, $10$, $25$, and $50\%$ replacement where available.
The complete comparisons and dose criterion are in Appendix~\ref{app:dose-ladder}.

\section{What specialized objectives add}
\label{sec:attrib}

A preservation method may help because it exposes the model to the reverse mapping.
The comparison asks whether its training objective adds a benefit beyond that exposure.
We compare auxiliary
methods with ordinary reversed-pair SFT and with controls that change exposure without
adding the proposed loss. Beating forward-only training is not enough to answer this
question. Table~\ref{tab:main-loss-baselines} reports both task directions.

\input{tables/main_loss_baselines.tex}
\paragraph{Methods and controls.}
Representation-alignment methods encode the two sides independently and train paired
representations to be similar, using a symmetric contrastive loss alongside forward-only
or mixed-direction CE. Negatives come only from training data. This exposes the paired
correspondence without applying backward generation CE. Shuffling the positive pairs tests
whether their correspondence matters; repeating ordinary CE on the same examples tests
whether extra predictive training can reproduce the benefit.
Contrastive fine-tuning (CFT) is a separate, code-specific reconstruction that trains
program-equivalence judgments with CE. Other baselines add instruction-conflict
unlikelihood or periodically generate a forward answer and train on its reverse mapping
with round-trip CE. Exact recipes and realized directional exposure are reported in the
appendix.

\paragraph{Generation results.}
Forward-only representation alignment does not consistently improve backward generation
beyond additional-CE or shuffled-pair controls. In code, CFT yields
\NUM{main-objective-code-llama32-3b-cft-backward}\% backward success versus
\NUM{main-objective-code-llama32-3b-mix5-backward}\% for $5\%$ reversed-pair SFT,
with each evaluated on the same examples as its base and controls. Forward-only
unlikelihood also fails to preserve backward translation in these experiments.
These comparisons establish why directional SFT is a necessary baseline.

Mixed-direction alignment sometimes improves on the $5\%$ mixture. In SQL/Llama8B,
round-trip training yields
\NUM{main-objective-sql-llama31-8b-roundtrip-backward}\% backward success versus
\NUM{main-objective-sql-llama31-8b-mix5-backward}\% for the mixture, while forward
success is \NUM{main-objective-sql-llama31-8b-roundtrip-forward}\% versus
\NUM{main-objective-sql-llama31-8b-mix5-forward}\%. These point estimates trade a small
forward decrease for a backward increase; their uncertainty is shown in
Table~\ref{tab:auxiliary-intervals}. Appendix~\ref{app:complete-main-comparisons} reports all primary
contrasts and their per-run uncertainty. Specialized objectives therefore need to be judged
against the directional baseline on both forward and backward performance.

\section{Why backward examples may help}
\label{sec:mechanism}

Correct-answer likelihood and generated correctness can move in opposite directions.
In Gemma translation, forward SFT lowers loss on correct backward answers even as backward
generation becomes worse. Correct answers becoming less probable therefore cannot alone
account for degradation across models: generation also depends on their probability
relative to competing outputs.

We hypothesize that forward-only updates bias which output the model selects for the
backward task, and backward examples help maintain that selection. Equation~\ref{eq:replacement}
shows how ordinary CE supplies direct supervision for this conditional; it could counter
the bias without a special alignment objective. Candidate comparisons support this account:
in formatting and translation, forward SFT reduces preference for correct backward answers
over copied inputs, while mixed-direction SFT increases that preference.

Layer interventions provide complementary evidence in formatting. Removing middle-layer
updates improves backward success beyond scaling and random-removal controls matched for
retained update norm, with small forward changes. This suggests selective interference in
that task. Gradient and local-update analyses provide no clear collapse-specific signature
and are reported with the complete comparisons in Appendix~\ref{app:mechanism-sprint}.

The evidence is exploratory. Restricted candidates do not cover all valid answers, candidate
lengths affect rankings, and the layer controls match retained norms rather than edit norms.
Multiple interventions in one task do not establish a general mechanism. These observations
support output-selection interference as a hypothesis; they do not demonstrate erased
knowledge or a general post-training repair.

\section{Related work}
\label{sec:related}
\paragraph{Directional degradation and reverse training.}
Code specialization \citep{nikiema2025contrastive}, direction-dependent translation loss
\citep{zhu2024finetuning}, and program-execution asymmetry
\citep{hasanov2026pathnottaken} motivate evaluating existing abilities in both directions.
The reversal curse concerns a reverse capability that was never acquired
\citep{berglund2024reversal}. Reverse training addresses direction at the data level
\citep{golovneva2024reversetraining}; we measure preservation across doses and compare
objectives against that supervision. Bidirectional behavior need not imply a unified
representation \citep{latentgen2026illusion}.

\paragraph{Forgetting, rehearsal and recovery.}
Forgetting after fine-tuning \citep{luo2023forgetting}, differences between LoRA and full
fine-tuning \citep{biderman2024lora}, and rehearsal \citep{scialom2022rehearsal} motivate
our controls. Wrapper and offset accounts \citep{jain2024wrapper,lee2024dpo}, skewed task
inference \citep{kotha2024forgetting}, and update filtering
\citep{spectral2026unforgetting} concern distinct explanations or later repair. Our
replacement intervention preserves during training; behavioral repair alone does not
identify a unique internal mechanism.

\paragraph{Objective attribution.}
Data mixtures can confound attribution \citep{longpre2023flan,lipton2018troubling}.
RevThink adds backward questions and reasoning \citep{chen2025revthink}, illustrating
why directional exposure matters even for a bidirectional objective. Reversed-pair SFT,
additional CE, and shuffled positives test what an objective adds without assuming
auxiliary objectives are universally unnecessary.

\section{Conclusion}
Training a model in one direction can damage an existing reverse-task ability. In several
tested settings, replacing a small fraction of forward examples with reversals preserves
much of backward performance while retaining most forward performance. The useful dose
and forward cost vary across tasks; some specialized objectives add further benefits.
The practical implication is to evaluate both directions and compare new preservation
objectives against ordinary directional supervision. Output-selection diagnostics help
interpret this result and remain a supporting hypothesis.

\section*{Limitations}
\label{sec:limitations}
\paragraph{Scoring and alternatives.}
Correctness is task-specific. Code execution on finite tests does not prove semantic
equivalence or readable-source recovery. Format equality normalizes scalar case and does
not enforce YAML-exclusive syntax. Algebra expansion lacks a separate expanded-form check,
and factorization need not be complete. Factual exact matching may reject aliases.
Translation thresholds differ by model/direction; its original forward predicate lacks
explicit echo rejection. SQL question correctness depends on a frozen parser that can
reject valid paraphrases. The proposed WebNLG text check fails on reference texts and
therefore cannot support a tuned comparison (Appendix~\ref{app:task-scoring}).

\paragraph{Scope and generality.}
Replacement cannot recover information absent from the input. Original code is Python-only;
translation covers English paired with German or Chinese. Synthetic variants and changed
output contracts reuse semantic corpora rather than supplying independent domains.
Some proposed tasks have inadequate starting bidirectional performance or unreliable
checks; Appendix~\ref{app:boundaries} reports these exclusions. Independent OPUS transfer
fails its copy-validity criterion, so it establishes no tuned preservation result.

\paragraph{Models, training and resolution.}
Coverage is uneven across five model sizes and training runs, and most comparisons use
LoRA. Full-weight checks cover selected Llama3B runs and do not establish a bound on other
recipes. Example and optimizer-step matching does not imply matched tokens or runtime.
Paired intervals quantify test uncertainty; training-run ranges do not establish an
optimal dose or equivalence between adjacent proportions. Changed prompts and recipes
can introduce forward costs or backward loss, including in the original units null case.
Historical upstream dataset revisions and training versions are incomplete, limiting exact
reconstruction beyond the retained corpora and result analysis.
